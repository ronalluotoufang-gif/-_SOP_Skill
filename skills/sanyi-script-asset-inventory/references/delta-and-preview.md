# 增量与预研模式

主流程是 `full`：正文已定稿，一次整理。实际工作里还有两种常见情形，需要不同处理。

## delta 增量模式

适用：已有上一版清单，正文有改动、集号重排或补写了新集。

输入：上一版清单 JSON、新正文、两版之间的集号／场次对应（若有重排）。

做法：

1. 先建新旧引用对照 `delta.ref_map`，例如 `E33A → E33`。**所有旧 `source_refs` 必须经此映射后重新核对**，不能只替换集号。
2. 逐条旧资产核对，给出去向：
   - `kept` 保留；
   - `upgraded` 升级（B→A，或新增了门）；
   - `downgraded` 降级（A→B／C）；
   - `removed` 移除（正文已删除相关内容）；
   - `relocated` 来源移位（内容在，场次变了）；
   - `added` 新增。
3. 对新增内容完整过一遍三门，尤其是 D 门；旧版没发现的难生成项往往在此时被补出。
4. 每条变化写 `reason` 和新来源。避免"悄悄消失"。
5. 资产 ID 尽量沿用；仅当同一资产被拆分或合并时才改 ID，并在 `delta.changes` 里写明。
6. 沿用旧版的 `needs_confirmation` 未解决项，逐条标"已解决／仍待确认"。

交付：HTML 增加"相对旧版变化"区；首页显示新旧 A 级数量。

## preview 预研模式

适用：正文还在改，但设计端需要先开工。

规则：

1. 只提取**稳定项**。稳定项判定：该设定在近期改稿中未被反复调整，并且与当前正在重写的段落无关。判断不了时，默认不稳定，不收。
2. 每条资产写 `stability`：`stable`（可开工）、`volatile`（可能被改，不要开工）。预研清单只收 `stable`，`volatile` 项写进待确认栏说明原因。
3. `meta.mode = "preview"`，`meta.provisional = true`。首页显示"预研／非正式"，数量不作为交付数字。
4. 不写按集新增表和声音调用表，避免集号变动后整张失效。
5. 正文定稿后，用 `delta` 模式把预研清单升为正式版：预研清单就是旧版，`kept` 为主，补充新增项。

## 为什么要分模式

资产清单的价值在"交给下游后不返工"。稿子没定就硬出一份完整清单，改稿后整张表需要重来，下游已经做的图也可能作废。预研模式把"能先做的"和"别急着做的"分开，delta 模式让旧清单可累积而不是每次重建。
